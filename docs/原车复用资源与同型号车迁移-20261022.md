# 原车复用资源与同型号车迁移清单

核查日期：2026-10-22。当前车为 T710/PaddlePi、aarch64；用户确认另一个实验室的主控、下位机型号相同。当前核查只读取文件和 ELF 依赖，没有加载模型、打开摄像头或串口。

当前入口为 `/root/track-trial-20261010/bin/trackview_race_appearance`。下面的相对路径均以该 `bin` 目录为工作目录。

## 一、直接沿用的原车资源

| 资源 | 实际路径或内容 | 作用 | 换车时的处理 |
|---|---|---|---|
| 已训练并部署的 YOLOv3 MobileNetV1 模型包 | `../res/models/yolov3_mobilenet_v1/deploy_paddle.*` | 原有检测网络在 T710 上的部署产物 | 同型号且运行库兼容时通常可复用；先核对文件和原车自带模型，当前没有重新训练 |
| 模型后处理 | 同目录 `post.onnx`、`io_paddle.json`、`nms.tar`、`nms.tar.so` | 张量对应关系、检测后处理、重复框筛除 | 作为同一套模型一起核对，不单独混搭另一套 |
| 类别顺序 | 同目录 `label_list.txt` | 将模型类别编号解释为具体目标 | 必须保持 15 类及顺序一致；不可随意换行或调换左右标签 |
| PPNC 配置 | `../res/models/config_ppncnna.json`、`config_ppncnms.json` | 告诉原推理器去哪里加载 NPU 模型和 NMS | 原配置格式沿用，项目副本里的模型路径已适配独立试跑目录；另一车新建副本后检查相对路径 |
| 相机内参与畸变参数 | `../res/calibration/calibration.xml` | 按 320×240 图像做去畸变 | 优先保留另一辆车自己的适配标定；相机、分辨率或安装变化后重新核对 |
| 原有系统库 | PPNC、ONNX Runtime、OpenCV 3.4、LibSerial、libevdev、libudev，以及其系统依赖 | 推理、图像处理、显示、串口和手柄读取 | 使用另一车原有兼容环境；同型号也不能跳过版本和设备认证检查 |
| 设备与下位机固件 | 摄像头、T710/NPU 驱动、USB 串口、原下位机控制固件 | 采图、推理，执行速度和舵机指令 | 此前没有在该试跑流程中刷写下位机；另一车通信协议和机械设置仍需确认 |

模型目录在当前车核对到的文件为：

```text
deploy_paddle.tar
deploy_paddle.so
deploy_paddle.params
deploy_paddle.ro
post.onnx
io_paddle.json
label_list.txt
nms.tar
nms.tar.so
```

这些是配套部署产物，不能把每个文件都理解成单独的一套神经网络权重。没有重新训练，也没有让小车调用 ChatGPT 或云端大模型；图像识别在车上的本地推理环境运行。

启动时的“nms模型编译完成”来自原检测器的 NMS 构建流程，不是重新训练 YOLO。它会解包 `nms.tar`，在当前 `bin` 下产生或覆盖 `lib0.o`、`devc.o`，并生成模型目录里的 `nms.tar.so`。这些文件的修改时间随启动变化属于该流程的正常现象。

当前模型、标定等可对照的资源与 10 月 20 日快照一致。系统库本次记录了版本、文件和依赖，但没有因此断言所有系统文件都有完整历史基线。详情保存在本地 `<实验资料目录>/vehicle_dependencies_20261022/current-vehicle.json`。

## 二、沿用并适配的原有代码基础

| 原有模块 | 当前使用方式 | 后续修改边界 |
|---|---|---|
| `src/detection` 检测器 | 沿用原有预处理、PPNC 推理、ONNX 后处理和 NMS 链路 | 新入口增加文件/标签检查、异步调用及结果时间戳；没有训练新模型 |
| `src/predeal` | 沿用相机去畸变、灰度和阈值处理流程 | 增加或保留输入、标定校验 |
| `src/track` 和基础数据结构 | 沿用道路边界提取基础，为 v6 与比赛入口提供边界 | 在此基础上做过修正及控制层改进，不宜说所有源码从未动过 |
| 串口协议和控制接口 | `/dev/ttyUSB0`，115200、8N1，原有帧头、速度字段、PWM 和校验格式 | 增加线程、超时和停车锁定等保护；协议格式沿用 |
| 手柄接口 | libevdev/udev 自动寻找手柄事件设备 | 保留手动介入，增加断连和停止处理 |

当前 C++ 舵机中值常量为 1500，限位为 1100—1900。这些是当前编译参数，不代表另一辆车的机械实测值。若另一车需要不同中值或方向，应单独调整和编译，不能凭型号相同认定转向完全一致。

## 三、后来新增的部分

- v6 控制层中的中线、转向平滑和质量管理等改进。
- 独立比赛入口、任务状态机、岔路几何判断、路牌连续确认和停车/限速策略。
- AI 独立推理线程、旧结果过期判断、匹配图像的显示与数据取证。
- 左右箭头的图像复核、顶部红色物体辅助几何排除。
- `trackview.json`、`race.json`、静态测试脚本、回放工具。
- `librace_npu_backend.so`：后来编译的接入库，内部调用原检测器及原模型。这个库不是原车训练出的模型文件。

旧 `icar` 主程序和原 `res/config.json` 不是当前比赛入口直接使用的运行入口/主配置。不能只修改旧配置就认为已修改当前比赛程序。棋盘格图片、标定评估文档属于标定辅助材料，不是当前每次启动都必须读取的文件。

## 五、到另一辆同型号车的顺序

1. 先只读盘点它现有模型、标定、库和设备，不覆盖其组员工程。
2. 在新的独立目录准备程序、接入库和配套资源；保留新车适配的相机标定和控制参数。
3. 若原车模型的文件、标签顺序及配套库与已测试版本一致，优先直接复用；不一致时先比较，避免混用。
4. 先测试 `--no-control` 的路牌识别、状态切换和终端停止，再验证舵机方向、中值和低速运动，最后上完整赛道做岔路测试。

只读检查脚本：`tools/read_car_compatibility.py`。它不自动决定“可以开车”，也不加载模型或调用硬件。

上传到另一辆车后可运行：

```bash
python3 ./read_car_compatibility.py
```

原项目不在常见位置时指定目录，例如：

```bash
python3 ./read_car_compatibility.py --root /home/bot
```
